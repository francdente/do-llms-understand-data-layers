Do LLMs Understand Backend Data-Layer Semantics?

A Controlled Study of Cross-Endpoint Issues

Francesco Dente1*, Dario Satriani2*, Donatello Santoro2, Enzo Veltri2, Paolo Papotti1

1EURECOM, France  ·  2University of Basilicata, Italy  ·  *equal contribution

Code and data Results Cite

The paper will appear in the EMNLP 2026 proceedings.

LLMs recognize a data-layer bug when it is described to them, but they rarely discover it on their own.

We test five models on 216 tiny backends. With the definition of the issue in the prompt, average F1 is between 0.73 and 0.94. Without it, it falls as low as 0.03.

The problem

LLMs are increasingly used to review code, not only to write it. Most evaluations check code against known bug patterns or an explicit specification.

Semantic data-layer issues are different. Nothing crashes, and every endpoint is correct on its own. The bug exists only across endpoints that share persistent state, so finding it means connecting the schema, the behaviour of each endpoint, and what the application is meant to do.

Three issue types

One per dimension of persistent state: who can see the data, whether it stays coherent, and whether it survives. None of these patterns is a bug by itself. Each becomes one only when a second endpoint observes the side effect.

Visibility exposed_record

Is the data visible to the correct reader?

A write changes a record's status, but a read endpoint still serves it without checking.

@app.post("/products/<pid>/discontinue")
def discontinue(pid):
    db.execute("mark as discontinued")

@app.get("/products/<pid>")
def get_product(pid):
    """Return a product
    available for purchase"""
    row = db.execute(
        "SELECT * FROM product "
        "WHERE p_id=?", (pid,))
    # no p_status filter
    return jsonify(row)

The read never filters on status: discontinued products are still served as if on sale.

Consistency stale_aggregate

Does the data stay coherent?

A write modifies source rows but does not update a stored aggregate that another endpoint returns.

# the invariant is stated only here
@app.post("/orders")
def create_order():
    total = "sum of lineitem prices"
    db.execute("insert order, "
               "o_totalprice=total")

@app.put("/orders/<oid>/lineitems/<id>")
def update_lineitem(oid, id):
    db.execute("update lineitem price")
    # o_totalprice never recomputed

Editing an item never recomputes the cached total: every later read returns a stale value.

Retention cascade_delete

Does the correct data survive?

A delete removes child rows that a read endpoint expects to remain observable.

@app.delete("/customers/<c_custkey>")
def delete_customer(c_custkey):
    # the customer's orders are
    # deleted in cascade
    db.execute("delete related orders")
    db.execute("delete customer")

@app.get("/orders/summary")
def orders_summary():
    """Return the summary of
    all historical orders"""
    return db.execute("orders summary")

Deleting a customer erases their orders: the summary silently loses the history it promises.

A deliberately small benchmark

Each task is a handbook-scale backend, scoped so that the only reachable defect is the semantic one under test. The schema and the code arrive in a single prompt, with no retrieval and no repository navigation, so every number here is an upper bound on real-world review.

  • 216task instances: 18 hand-written scenarios, each in 12 variants
  • 3languages (Python, JavaScript, Go), with raw SQL and ORM variants
  • ~53lines per backend: 1 to 2 tables, 2 to 3 endpoints
  • 50%of the instances contain the issue, 50% do not
  • 5models: GPT-5.4, Kimi-K2.6, DeepSeek-V3.1, Gemma-4-31b, Qwen3.5-397B

FREE

An open-ended review of the backend's data layer, with no hint. Measures discovery.

DEF

The prompt includes a natural-language definition of the target issue. Measures recognition.

The tasks are solvable from code and schema alone: 10 developers with 3+ years of experience reviewed them under the FREE conditions, and every issue type was found by at least three of them.

Three findings

Discovery gap

Removing the definition drops average F1 from 0.91 to 0.85 for visibility, from 0.94 to 0.56 for consistency, and from 0.73 to 0.03 for retention. The gap is statistically significant for consistency and retention, exactly where models fail to find the issue unprompted.

Hierarchy of detectability

Visibility issues are often found unprompted, consistency issues sometimes, retention issues almost never. Models spot what resembles familiar security practice more readily than latent data-integrity invariants. Developers show the same ranking.

Compliance bias

With the definition, models never miss the issue, but in retention they also flag 74% of the backends where it is absent (21% for visibility, 14% for consistency). They react to the cascade delete named in the definition, not to whether any data is actually lost: a harmless cascade delete is flagged in 119 of 120 cases.

Targeted detection benchmarks overestimate what a model finds in an open-ended review.

Reproduce the numbers

The repository ships the benchmark, the prompts, and every model output behind the paper's tables, so the results can be recomputed without API keys.

git clone https://github.com/francdente/do-llms-understand-data-layers
cd do-llms-understand-data-layers
uv sync
unzip data/results.zip -d data
# main results table
uv run reproduce_table.py
# FREE scores from the manual annotations
uv run compute_free_from_annotations.py

The README maps every table in the paper to the script and data that produce it.
